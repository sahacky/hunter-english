## 📋 КОНТЕКСТ ПРОЕКТА

### Концепция
Веб-приложение для изучения английского **с нуля (A0) до продвинутого (C1)** для русскоязычного пользователя. Цель — **путешествия**: понимать людей на слух и отвечать.

Ключевые идеи (подробности — `research/`):
- Методика: короткое правило → много построения фраз RU→EN (метод Бебриса «Английский до автоматизма») → слух (диктант) → речь (shadowing, микрофон) → интервальные повторения (SRS, FSRS).
- Контент: частотная лексика (NGSL-Spoken 721 → NGSL 2809 → до ~5000 по субтитрам), 8 основных времён + модальные, пунктуация, ловушки для русскоязычных, разговорник путешественника.
- Мотивация: фразы из сериалов/аниме/игр (Supernatural, GoT, Breaking Bad, Berserk, FMA, Solo Leveling, JJK, AoT, Stranger Things, Black Mirror, LOTR, Star Wars, The 100…) — только короткие текстовые цитаты с источником.
- Геймификация в стиле Solo Leveling: ты — «Охотник», ранги **E→D→C→B→A→S** привязаны к CEFR, повышение ранга только через экзамен «Врата»; XP, стрики с заморозками, ежедневные квесты.
- Озвучка — **британский английский (en-GB)**: заранее сгенерированное аудио (Piper `cori` + Kokoro `bm_george`) + фолбэк Web Speech API. Транскрипции не нужны.
- Режим: 1 час в день; сначала десктоп (Chrome/Edge), затем мобильная версия (PWA) с общим прогрессом.

### Целевая аудитория
Личный проект: один пользователь (разработчик), русскоязычный новичок. Репозиторий приватный (GitHub), прогресс — в Supabase.

### Стек технологий
Vite + React + TypeScript · Supabase (Postgres, Row Level Security, вход через GitHub) · Dexie (IndexedDB, офлайн-first) · ts-fsrs · react-i18next (ru/en) · vite-plugin-pwa · Vitest + Playwright · ESLint + Prettier · Python-скрипты для подготовки данных · GitHub Actions → GitHub Pages.

### Архитектура
```
[ GitHub Pages ]  статический SPA (hash-роутинг), учебные данные (JSON), аудио
       │  HTTPS
       ▼
[ Supabase ]      Auth (GitHub OAuth) + Postgres: профиль, card_state (FSRS), review_log, прогресс уроков
[ Браузер ]       IndexedDB (Dexie) — локальная копия прогресса, очередь синхронизации, офлайн
```
- Синхронизация: запись сначала в IndexedDB → очередь → upsert в Supabase; `review_log` append-only; конфликты по `updated_at`.
- Структура репо (черновик): `research/`, `data/` (CC BY-SA), `audio/`, `scripts/` (Python), `src/`, `supabase/` (SQL, RLS), `CREDITS.md`, `.github/workflows/`.
- Лицензии: код — MIT; `data/` — CC BY-SA 4.0; источники в `CREDITS.md`. **Oxford 3000/5000 не публиковать**, видео/аудио из сериалов не класть в репо.

## 🧠 РОЛИ И ГРАНИЦЫ ОТВЕТСТВЕННОСТИ

| Роль | Обязанности |
|------|-------------|
| **AI-агент** | Генерация кода, запуск тестов, обновление WAL/PLANS, следование плану, задавание уточняющих вопросов |
| **Разработчик** | Архитектурные решения, выбор между альтернативами, код-ревью, финальный push, разрешение конфликтов |

AI — сопроцессор, а не подчинённый: сильные стороны AI — пропускная способность генерации кода, механическая согласованность, формальные структуры; сильные стороны человека — семантические решения, кросс-сессионная когерентность, архитектурное суждение.

**Золотое правило:** Если решение влияет на архитектуру, выбор технологий или структуру БД — AI не принимает его самостоятельно. AI предлагает 4 варианта и ждёт выбора разработчика.

**Никогда не делай без явного подтверждения:**
- Удаление файлов или директорий
- Запуск миграций БД в production-окружении (Supabase)
- Установка новых npm/pip-пакетов без обоснования
- Изменение файлов, помеченных в WAL как "Watch out: DO NOT MODIFY"

## 📚 ВЕРСИОНИРОВАНИЕ WAL И PLANS

WAL.md и PLANS.md имеют секцию **Changelog**:

```markdown
## 📜 Changelog

| Дата | Изменение | Причина |
|------|-----------|---------|
| 2026-03-21 | Добавлена задача M1#3 | Уточнение от разработчика |
```

Правило: каждое изменение WAL/PLANS (кроме отметки чекбоксов) требует записи в Changelog.

### Формат WAL.md
- WAL (Write-Ahead Log) — «сейвпоинт» для следующей AI-сессии, а не история и не отчёт.
- До ~3000 токенов. Завершённые элементы коллапсировать в одну строку.
- Содержит: что делать дальше, где делать, что НЕ трогать, какие решения ждут, какие тесты запустить.
- Анти-инструкции ("Watch out: не трогать X") критически важны — защищают от поведения «я вижу, что можно улучшить».
- Обновлять: в конце каждой сессии; перед деструктивной операцией; при переключении модуля; превентивно в длинной сессии.

### Правила PLANS.md
1. PLANS.md — единственный источник правды о том, что нужно сделать.
2. Чекбоксы `[ ]` / `[x]`; отмечать сразу после завершения (по «Определению завершённой задачи»).
3. Майлстоуны выполняются последовательно, если не согласовано иное.
4. Изменения плана — только после обсуждения с разработчиком, с записью в Changelog.
5. Не придумывать задачи.

3. Если в WAL есть пометка `[RECOVERY]` — сначала восстанови последнее известное рабочее состояние.

### Если обнаружено противоречие в планах/коде:
1. Остановись и сообщи о противоречии с точными ссылками: `plan://...#A` vs `plan://...#B`.
2. Предложи 4 варианта разрешения.
3. Не продолжай работу, пока человек не выберет вариант.

### Если тесты не проходят после твоих изменений:
1. Не игнорируй падение. Не «чини» тест, подгоняя его под код.
2. Проанализируй: код не соответствует плану ИЛИ план устарел.
3. Если код неверен — исправь код.
4. Если план устарел — добавь REVIEW-маркер и сообщи человеку.

### Если человек дал команду, противоречащую плану:
1. Выполняй команду человека (приоритет: Человек > План).
2. Добавь предупреждение: "⚠️ Это отклоняется от plan://...#section. Обновляю план?"
3. Если человек подтверждает — обнови план и зафиксируй в WAL.

### Если обнаружил секрет в Git-истории:
1. Немедленно остановись и сообщи: «⚠️ Обнаружен секрет в истории Git».
2. Не делай новых коммитов.
3. Предложи 4 варианта:
   1) Переписать историю (git filter-repo / BFG)
   2) Откатить до коммита до утечки
   3) Инвалидировать скомпрометированный ключ
   4) Продолжить (не рекомендуется)

## 💬 ПРОТОКОЛ ВЗАИМОДЕЙСТВИЯ

### Когда задавать вопросы:
- Если задача неоднозначна или противоречит плану.
- Если есть несколько валидных подходов с разными последствиями.
- Если требуется архитектурное решение.
- Если обнаружен Known Issue, блокирующий задачу.

### Формат вопросов (ОБЯЗАТЕЛЬНО):
Предлагай ровно 4 варианта ответа. Пользователь выбирает цифру 1/2/3/4 (или пишет свой).

```text
❓ Вопрос: <суть>
1) <вариант А + краткие плюсы/минусы>
2) <вариант Б + краткие плюсы/минусы>
3) <вариант В + краткие плюсы/минусы>
4) <отложить решение, продолжить по текущему плану>
```

### Работа с планом (PLANS.md):
- Не придумывай задачи. Делай только то, что в плане или явно согласовано.
- Если обнаружена новая необходимая задача:
  1. Предложи её добавление в план с оценкой и приоритетом.
  2. Дождись подтверждения.
  3. Только потом добавь в PLANS.md (с записью в Changelog) и начинай работу.

## ⚛️ АТОМАРНОСТЬ ИЗМЕНЕНИЙ

- Один коммит = одна логическая задача = одна ссылка на план/спеку.
- Запрещено смешивать в одном коммите: рефакторинг + новую фичу + исправление бага.
- Формат коммита (Conventional Commits, на английском):

```text
<type>(<scope>): <short description>

Implements: plan://M2#task-1
<detailed body: почему и как принято решение>
```

## 🚫 ЧТО НЕ ДЕЛАТЬ НИКОГДА

| № | Запрещённое действие | Почему |
|---|---------------------|--------|
| 1 | Не молча меняй значения в планах/спеках | Нарушает согласованность и доверие |
| 2 | Не смешивай несвязанные изменения в одном коммите | Усложняет ревью и откат |
| 3 | Не начинай работу без чтения WAL/PLANS и подтверждения понимания задачи | Ошибки и несоответствие контексту |
| 4 | Не игнорируй сломанные тесты | Маскирует проблемы |
| 5 | Не оставляй сессию без обновления WAL | Потеря контекста |
| 6 | Не генерируй код "на будущее" — только по задаче из плана | Лишняя сложность |
| 7 | Не предполагай намерения человека — уточняй | Риск сделать не то |
| 8 | Не коммить секреты и креды | Компрометация |
| 9 | Не делай push без явного разрешения | Контроль над репо |
| 10 | Не работай в `main` напрямую | Обход ревью |
| 11 | Не удаляй файлы без подтверждения | Потеря данных |
| 12 | Не запускай destructive-команды (миграции, удаление данных) без подтверждения | Необратимость |
| 13 | Не клади в репо видео/аудио из сериалов и Oxford-списки | Авторские права (публичный репо) |
